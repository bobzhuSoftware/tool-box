# 探测记录：新平台 ServiceCentral（2026-11-15）

目的：确认新平台的链接格式、登录与取数方式是否能沿用，以及旧链接能否只换域名迁移。所有探测都是只读的，只打开页面和发 GET 的 REST 请求，没有改动 ServiceNow 数据。

环境：Windows，Edge 自动化会话（使用已保存的登录身份 `default`），账号 `bob.zhu`。探测脚本是临时的，不在仓库里；仓库里的 [tools/servicenow_probe_page.py](../../tools/servicenow_probe_page.py) 可以做第 2 节的页面请求记录。

## 1. 登录

- 沿用已保存的会话，无头模式下直接登录成功，最终停留在新域名，没有 SSO 跳转到别的域名。
- `window.g_ck` 存在，`GET /api/now/ui/user/current_user` 返回 `bob.zhu / Bob Zhu`。
- 原来 `_on_servicenow` 只认 `service-now.com`，在新域名上会一直等到超时，所以先放开了域名规则（见 [README.md](README.md)）。

## 2. 页面请求与 saved-list 的读取

页面初始数据里有 `"route":"list"`、`params.listId`、`params.tinyId`、`wasTinyURLResolved:false`，另外 `g_uxr_tiny_url.use_tiny = true`、`min_length = 2000`：`tiny-id` 就是 ServiceNow 的 tiny URL 机制。

页面加载列表时的关键请求：

| 请求 | 说明 |
|---|---|
| `POST /api/now/uxf/databroker/exec/macroponent` | 返回 `errors: ["Cannot read property \"mappingGroups\" from null"]`、内部 status 500。页面自己的噪音，之后列表仍然正常加载 |
| `POST /api/now/graphql`，`nowRecordListMenuConnected` | 返回左侧列表菜单（分类 "EDI Cases" 等） |
| `POST /api/now/graphql`，`nowRecordListConnected` | 变量里是 `tiny`；响应里 `GlideListLayout_Query.getTinyListLayout` 带完整的列表定义 |

`getTinyListLayout` 的内容：

| 字段 | 值 |
|---|---|
| `listId` | `81b0d3a9c3d81f104837e645990131fa` |
| `tiny` | `lqkiN0e1Ej9Xtezn3MjPkdHk4VIVFaRA` |
| `listTitle` | `Cases Received Last 7 days Blue` |
| `tableLabel` | `EDI Case` |
| `layoutQuery.table` | `x_dsva2_enterpri_0_edi_case` |
| `fixedQuery` | 空 |
| `query` | `origin_of_request!=schenker_origin^state!=1000^state!=1300^division=420b49d01b3ae5103620b6c5464bcb89^sys_created_onBETWEENjavascript:gs.beginningOfLast7Days()@javascript:gs.endOfToday()^assignment_group!=2dafd3ec2b6d7690db00f454c891bf54` |
| `layoutQuery.count` | **17** |

这条 `query` 和旧平台那条 simplelist 链接里的条件逐字相同。无头和有窗口模式下得到的响应一致（响应体长度相同，count 都是 17）。

## 3. 新旧域名对比

用同一组条件（同一张表）分别在两个域名下读取：

| 来源 | 新平台 `servicecentral.dsv.com` | 旧平台 `dsv.service-now.com` |
|---|---|---|
| saved-list 页面 `layoutQuery.count` | 17 | 不适用（旧平台没有这条链接） |
| simplelist 页面 `layoutQuery.count` | 17 | **0** |
| REST `stats`，7 天筛选 | `17` | `0` |
| REST `stats`，不带条件的总数 | `8567` | `8424` |

结论：新旧平台的表结构和条件值通用，旧域名仍能登录和打开，但数据已停止更新，7 天筛选得到 0。继续用旧链接会得到错误的数字。

|---|---|

## 5. 排查过程中的注意事项

- 一开始用探测工具无头打开 saved-list 链接，只看到 1 个 `/api/now/` 请求（上面的 macroponent 500），没有 GraphQL，差点误判成"链接失效"。后面的对照实验里无头模式也能得到 GraphQL 响应，所以第一次更可能是等待时间或页面启动没有完成，不是平台限制（原因没有进一步确认）。以后判断"页面没有返回列表信息"时要多等一会儿，不要只看第一次。
- 用 REST 直接查 `list-id` 对应的记录（`sys_ux_list`、`sys_ux_list_category`、`sys_metadata`）都是空结果，另有几张表（`sys_ui_list`、`sys_ux_list_menu_config`、`sys_ux_page_registry`）返回 403。`list-id` 不是普通用户能通过 REST 读到的记录，所以不要尝试通过 REST 解析它，用页面的 `getTinyListLayout` 即可。
- 无头模式下 `page.screenshot` 会卡在等待字体，超时。截图要用有窗口的模式，或者不截图。
